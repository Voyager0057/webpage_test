# GRP 完成计划：2026-10-20 至 2027-04-30

编制日期：2026-10-20，时区 Asia/Shanghai。这里将用户所说的“到4月份”解释为 **2027年4月30日前完成**；若学院实际截止日更早，应整体前移最终验收与冻结日期。

本仓库当前交付的代码是项目起点。以下是团队从现在开始完成核对、理解、改进、实验与正式提交的计划，不把未来任务写成已经完成，也不要求把现有可用代码全部重写。已经通过验收的功能对应周次改为独立复核、边界补充和证据归档。

## 1. 排期假设与假期口径

### 1.1 人员与工时

- 4名成员，每人常规每周投入10小时，约每天2小时；忙碌周最高12小时只作个人自愿机动，不预先计入承诺。
- 按周一至周五排期，周末不安排强制任务，也不把法定调休补班周末自动加入学生项目工时。
- 标准周团队可用40小时，只承诺32小时，剩余8小时用于课程冲突、返工、政策核对和突发问题。
- 4天短周团队可用32小时，只承诺24小时。例会、代码审查、报告写作都包含在承诺工时中。
- 学校考试周与寒假尚未提供；春节之外的学校停工若超过缓冲，需要在第1周取得校历后重排。

## 6. 实验与报告交付

### RQ1：联合优化在哪些场景有效？

- 当前仓库提供 `experiments/run.py`、`experiments/results.json` 与 `experiments/comparison.csv` 作为先导实验起点。它们包含实际运行的小规模合成案例，不能直接称为200—300场景的正式实验或真实家庭数据；最终以文件中的实际样本数量和版本为准。
- 相同房价、首付预算、可贷边界、利率与目标口径。
- 比较原方案、仅调整房贷、联合模型方案；可调整的税务变量必须真实存在。
- 保留没有改善和没有可行方案的结果；报告金额差，避免对零/负基数计算失真改善率。
- 以约200—300个预定义合成场景为目标规模，最终按真实运行数报告；固定种子，保存输入、输出、版本与脚本。

### RQ2：性能改进是否保持结果正确？

- 小网格全枚举是参考答案；优化版使用相同候选集合和可行性条件。
- 报告一致性、候选数、淘汰比例、运行时间及机器/JVM参数。
- 缓存冷启动与热启动分别记录；JVM预热后重复测量，不能仅报告一次最快值。
- 未达到预期加速也如实讨论；性能不能以错误省略约束换取。

### RQ3：用户是否理解推荐？

- 使用匿名演示数据，任务固定为输入、找方案、解释利息取舍、找无解原因。
- 记录实际完成率、耗时、错误、访谈摘录；小样本只支持形成性改进。
- Codex可整理材料，但参与者、反馈和同意记录必须真实。

报告应覆盖：背景与相关工作、需求、政策与数学模型、架构与实现、正确性测试、实验评价、局限性、团队贡献与反思。每个核心要求映射到一个实现位置、一组测试和一个演示步骤；详细目标见 `REQUIREMENTS.md`。

| 计算错误 | 参考案例或守恒失败 | 冻结拓展，修复并回归所有相关指标 |
| 2027调休变化 | 正式通知新增停工工作日 | 扣减容量，先用缓冲，必要时删减可选拓展 |
| 学校考试/寒假 | 可用容量减少超过20% | 提前调整范围；不转为假期强制工作 |
| Docker或跨平台环境受限 | 本地只能运行一种环境 | 保留本地可运行路径，标注未验证平台；在有条件设备补验 |
| 实验无明显收益 | 联合变量不改变税务结果 | 保留结果并分析解耦原因；不挑选有利案例 |
| 工期不足 | M2或M3延迟超过一周 | 取消多城市、账号、随机模拟、提前还款；保护基础正确性和报告 |
| 答辩依赖网络 | 演示环境或联网异常 | 本地启动、固定案例、录像和结果文件三套备用 |

## 8. 最终提交检查

- 功能覆盖题目：工资与个税、公积金、两种还款方式、组合贷、约束优化、方案比较、界面与跨平台。
- “已实现”“已测试”“未来计划”分别写清；生成Docker或CI配置不等于已经在对应环境通过。
- 至少一电脑操作系统与一移动操作系统有实际操作记录；浏览器模拟视口另列。
- 政策和数据有来源、日期、版本及适用限制。
- 实验结果可重跑，图表来自归档数据。
- 报告、代码、演示版本一致；小组成员能解释自己的贡献与关键设计。
- 2027-04-23前准备好可提交材料，最后一周用于缓冲；不把最终新功能押在4月30日。
